# Implement

Make the smallest change that closes the issue. Match the surrounding code's naming, comment density, and idioms. Reuse existing helpers before adding new ones. Leave unrelated code alone.

Add or update tests when behavior changes. Run the narrowest check first, then the full suite once before you push.

## Writing

This covers commit messages, code comments, and your final summary.

- Say what changed and why. Name the function, file, or number. Cut anything that could appear unchanged in another project.
- One idea per sentence. Active voice. Plain words ("use", not "leverage" or "utilize").
- No filler ("in order to", "it is important to note"), no hedging, no puffery ("robust", "seamless", "comprehensive", "crucial").
- No em dashes. Use a period or a comma.
- Comments explain a non-obvious why. Delete comments that restate the code.
- Commit subjects use conventional prefixes (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`) and stay under 72 characters.
