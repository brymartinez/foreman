# Foreman

Coordinate one issue through four roles: planner, implementer, self-reviewer, and adversarial reviewer. Keep a planner and implementer context for the task; start a fresh read-only context for each code review. The coordinator owns scope, revision checks, publication, and handoff. Use Git, the issue tracker, and the host's agent tools. This skill does not require the Foreman CLI.

## Start or resume

- Open the specific issue the user selected. Require the exact `triaged` label. In chronological order, use comments headed `## Triage decisions` or `## Triage correction`, with source links. Use the issue description if there are none. Ordinary discussion does not set scope. Stop if confirmed scope is unreadable or material decisions conflict. For Linear, verify the target repository from an explicit link or the user's selection; ask if ambiguous.
- Read repository instructions. Verify the repo, remote, base, branch, worktree, existing PR, and active GitHub account before writing. Check the intended commit identity and push destination before commit or push. Reuse the task's checkout and branch if their identities match. Use a separate worktree for a new implementation when needed to isolate it. Stop on unexpected changes or an ambiguous branch or PR rather than overwriting work.
- Check early that the host can run both reviews with isolated contexts and read-only permissions. Surface a missing capability before publication. If the user wants local work to continue, keep the missing review gate visible.
- Keep one coordinator per issue. Do not resume over another active run or a live Foreman task. Save a checkpoint in a task-local file outside the commit, or in the conversation if durable storage is unavailable. Record issue and repo, branch and worktree, current stage and next action, scope and plan snapshots or hashes, decisions and outstanding questions, role handles when available, PR and proposed text, base and head SHAs, review ranges and verdicts, check results tied to a SHA, and retry counts. Before an external write, record the intended write; afterward, read back its result. On resume, reconcile with Git and the tracker before retrying. If a write may already have happened, look for its result before repeating it. Reuse the same planning or implementation context when possible; pause if it is lost and replacement is not authorized.
- Reread confirmed scope at each stage boundary and before publication or handoff. If the label disappears or the tracker cannot be read, pause. If scope or the checked plan changes, invalidate the old plan and review coverage, reconcile the plan, and apply it before reviewing again. Check any published plan against the saved snapshot rather than treating edits as automatically approved.

## Plan

Give the planner confirmed scope and its sources. Read enough repository code and instructions to ground the plan; leave the code unchanged. Produce two short documents:

- **Requirements**: numbered, verifiable statements of what must work, including limits and behavior to preserve.
- **Work plan**: ordered steps naming the code area, requirement IDs, and the observable behavior to test.

Check that the requirements cover confirmed scope and that the plan covers every requirement. Bundle unresolved product or technical decisions into a short question set. Save both documents; when authorized to publish them, create or update the two issue comments by stable marker or saved ID. Honor any required plan approval before implementation.

## Implement and verify

Give the implementer the checked requirements and plan, repository rules, and any recorded answers. Use the plan as the task specification. If it conflicts with the code or misses a material decision, preserve progress, state the exact blocker, and ask. Keep work on the task branch. Use behavior tests for acceptance criteria where appropriate and run focused checks after each fix. Run the repository's full supported suite, within the user's test permissions, before the first review. Record commands, exit results, omissions, and the tested commit; report an unavailable suite with a concrete reason. A known failure is not an unavailable check. Create a clean checkpoint commit when authorized and verify the worktree and revision before review.

Prepare PR text using the repository's template and issue-linking rules, including requested evidence. Foreman's standard flow opens the PR after initial validation and before review. If the user chooses local review first, keep the commits and fixes local until both reviews and final validation cover the candidate. If external writes are outside the authorized scope, continue locally and leave publication pending.

## Review, fix, and repeat

1. Pin the base ref and its current commit, plus the candidate head. Check mergeability with Git or the PR's verified GitHub state. If an authorized repair is needed, merge the current base in the task branch, run focused checks, and confirm the new head contains that base; never rebase or force-push. Repeated conflicts on the same head/base or an uncertain repair require a decision.
2. Start with a fresh read-only self-reviewer using the implementer's provider when available. Then use a fresh read-only adversarial reviewer on a competing provider. Give each only the working directory, pinned diff command, and review rules; keep the issue, plan, decisions, PR text, implementation history, and previous findings out of its context. Reviewers can read adjacent code and tests. Use genuinely isolated, read-only agent tooling. If the host cannot provide it or a reviewer is unavailable, report the missing gate and pause; any user-approved substitute must be labeled.
3. First pass for each reviewer: `git diff --no-ext-diff --no-textconv --ignore-submodules=none BASE...HEAD --` with commit SHAs. On a fix pass, use `REVIEWED_HEAD..FIXED_HEAD` only if Git confirms ancestry, the base is unchanged, and the range is nonempty; otherwise restart with the full diff. Reviewers return an explicit clean verdict, concrete findings with file/line, failing case and impact, or a blocking limitation. Truncation or a skipped diff cannot count as clean.
4. Return findings to the retained implementer. Account for each with a fix and focused checks, or evidence that it is invalid. Send the fix to a fresh pass of the reviewer that raised the findings. Self-review must clear before adversarial review starts; adversarial fixes go back to adversarial review. The implementer cannot waive an adversarial finding. Pause after three fix rounds unless the user authorized another limit. Quota, errors, and session loss never count as review. A changed scope, base, retarget, or unrelated new commits invalidate the applicable coverage; restart both reviews when the baseline changes.
5. Before local-first publication or handoff in either mode, confirm that the full suite covers the final head. Reuse a passing result from an ancestor only when repository-specific evidence shows **every** changed path cannot affect behavior or validation inputs. A filename alone is insufficient. Otherwise run the permitted suite on the final head. If validation adds a fix, review the new commit before advancing. Stop after three final-check attempts without coverage. If no full suite can be identified, record the reason and hand off explicitly unverified; a required check that fails or cannot run needs a decision before advancing.

## Publish and hand off

- When authorized, look for an existing PR for the task branch first. Adopt it only if it matches the expected task and stage; pause if it conflicts. Otherwise push the verified candidate SHA without force and open the PR with the prepared title and body. For local review first, verify that the worktree is clean, the SHA matches the reviewed candidate, and the title and body match the proposal you checked separately against the plan and PR template. Read back the PR's repository, state, head, base, and title/body. Attach requested screenshots only where authorized and avoid duplicate comments on retry. Do not merge.
- Check all CI checks on the actual PR head using `gh pr checks` or equivalent. Pending checks mean **waiting for CI**; an API error is not a no-checks result. Watch within the active task when possible; if observation ends, save the checkpoint for a later resume. When checks finish, re-read the head and base and make sure review and validation still cover them. Hand back a cleanly reviewed PR with its CI result, including links to failures or an explicit no-checks result. Leave CI fixes and PR conversation to the user unless separately requested. A closed PR stops the run; a merged PR is done.
- Report the PR URL or local commit, covered revision, checks, and current stage. If paused, name the missing decision or evidence and the exact next action.
